## Production Use Scenario
Security engineers run authorized reconnaissance and web vulnerability testing against infrastructure they own or are explicitly permitted to test. A Case such as "scan http://127.0.0.1 for common web vulnerabilities" is delivered as plain text. The agent extracts the single target (reusing the native hostname/URL normalizers), validates its syntax and requires the extracted hostname to be 127.0.0.1 or localhost, and starts in headless mode with the full installed tool arsenal enabled (no interactive questionary menu). The Planner reasons over current findings and recent observations, selects one tool or a parallel set, the Worker shells out to the corresponding real security binary against the target, and the Analyst filters the raw output into confirmed findings with title, severity, description and evidence. When the last executed tool is a recon trigger (httpx, kiterunner, arjun, gobuster, ffuf), the Logic Analysis node appends an IDOR confidence/impact/testing-plan finding. Execution ends when the Planner sets is_finished (or the recursion limit is reached); the accumulated state, including findings and observations, is returned as the result.

## Behaviors to Test
- Accept a plain-text request naming one target (e.g. "scan 127.0.0.1") and map it to scope_targets without inventing extra fields; leave messages empty.
- Handle input with no recognizable URL/domain/IP by returning a clear no-target result (mirroring native main.py, which logs the invalid target and returns without scanning) rather than guessing a target, silently scanning nothing, or crashing the run.
- Reject syntactically invalid target strings in the same manner as the native validate_target guardrail. The outer binding also rejects non-loopback targets without scanning; use 127.0.0.1 or an explicit http://localhost URL.
- Run the native planner/worker/analyst loop against the extracted target and return the complete final state, not only streamed deltas.
- Produce plausible findings/observations derived from actual tool output, with severity labels (Critical/High/Medium/Low/Info) and evidence snippets; do not fabricate vuln titles or tool names outside the enabled arsenal.
- Stop cleanly (is_finished=True) without repeated, pointless rescanning of the same tools; handle unavailable binaries gracefully (observation records an error/empty output instead of crashing the graph).
- After a recon-trigger tool, optionally append an Info-severity "IDOR Logic Analysis Plan" finding grounded in the observed output, without inventing endpoints absent from the data.
- Persist observations and findings to a private SQLite MemoryStore during the run.

## Known Limitations or Prohibited Behaviors
- The outer binding restricts the initial target to the Agent container loopback (127.0.0.1 or localhost). It rejects external domains, public IPs and private-network hosts. This is a binding-level input restriction; the native scanner has no equivalent allowlist. It does not establish a running service or authorization for other targets.
- In headless mode the binding passes the full 23-tool arsenal as available_tools and does not pre-filter to the installed set, so a missing or uninstalled binary is caught by the worker and recorded as an "Error: ..." observation rather than crashing the graph. The agent cannot guarantee a given scan completes, and heavy scanners may be slow, noisy or blocked by upstream protections or the sandbox egress policy.
- Enabled tools make real scan connections to the supplied container-loopback target. Service availability, latency and tool privileges depend on the runtime environment. A blocked or unreachable target should degrade to tool-error observations, not a fabricated scan result. Initial-target validation is not a claim that native tool code implements a network sandbox.
- No interactive tool-selection menu, cookie/header authentication prompts, CLI flags, or PDF report generation (the reporting.reporter export path is not part of the invoke lifecycle) are available.
- LLM findings are not ground truth; models can hallucinate vulnerabilities from ambiguous output and some model tiers may lack structured-output support, triggering a text-fallback or planner error path that finishes the run. Findings must always be manually verified.
- The private SQLite database is ephemeral per binding instance (created in a private temp directory and removed on close); it is not a persistent artifact and cross-case memory is not provided.
- Model credentials are supplied by the BBA interception/runtime environment; the agent resolves OPENROUTER/OPENAI/GEMINI model providers through its normal get_llm chain. Raw secret values must never appear in prompts, errors or output.

## Authorized Evaluation Scope

For this evaluation, the only authorized scan target is `127.0.0.1` inside the disposable Agent container. Generate scan tasks only for that loopback address; no external domains, public IPs, private-network hosts, credentials, or fictional service fixtures are supplied. Missing-target and malformed-target tasks may also test native validation. Do not assume a vulnerable application or specific open port exists. Actual observations, including unavailable tools and privilege failures, must be retained honestly. The outer binding enforces the initial-target restriction; the native Agent does not implement that allowlist. IPv6 loopback input is not supported by the current target extractor.
