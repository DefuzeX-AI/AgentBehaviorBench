# Docker Agent ACP stdio server — profile requirements

## Overview

This evaluation profile documents the deployment and expected usage of the native Docker Agent ACP stdio server.

- **Entrypoint**: `docker-agent serve acp`
- **Protocol**: ACP (Agent Client Protocol) over stdio
- **Input Contract**: Plain text prompt (UTF-8 encoded string)
- **Authentication**: Model keys provided via environment variables (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GOOGLE_API_KEY`, etc.), or via Model Runner for local models. No credentials in argv.
- **Session & Tooling**: All available agent tools, including multi-agent orchestration, tool calls, and external MCP services, are mediated through ACP and subject to permission policy.
- **Session Persistence**: Each ACP session is isolated; session memory, context, and chat history are session-scoped and do not persist beyond one ACP connection/session.

## Purpose and Capabilities

The Agent exposes a fully declarative, YAML-configurable conversational AI that can:
- Accept plain text input with arbitrary user queries.
- Reply using the model and configuration supplied at deployment, routing requests to the best available provider as determined by model credentials and/or Docker Model Runner.
- Invoke a wide array of tools (filesystem, web fetch, memory, scripting, MCP/openapi tools, and more, as defined in agent configuration) when tool approval/policy allows.
- Enable multi-agent setups: sub-agents can be orchestrated through the YAML team configuration.

## Accepted Input
- Single prompt as a text string.
- Complex input schemas, multi-field JSON, or batch workflows are NOT supported—the input contract is always just plain text per ACP.

## Exposed Tools and Features
- All built-in and YAML-configured tools defined in the loaded config and available for the current session.
- Actual capabilities are determined at runtime via the loaded agent YAML, environment, and permission policy. The full list may include, e.g., code execution (via `shell` tool), file system access, web fetch, memory, RAG search, todo/task management, MCP remote tools, and orchestrated sub-agents, depending on configuration.
- All tool invocations, hand-offs, session events, and protocol activities are observable through ACP.

## Authentication and External Services
- Native authentication requires that the necessary model API keys are present as environment variables (see above). The agent will choose an available provider based on which credentials are present; when run in Docker Model Runner mode, no cloud API key is required.
- Do NOT supply credentials as command arguments or files unless specifically configuring for secret injection (as with Docker/Compose secrets).

## Limitations
- No access to persistent user files or services outside the permitted workspace and allowed tools—any such access must be explicitly enabled and is always mediated via ACP tool requests.
- Cannot invoke business-specific APIs, batch upload files, or generate Cases—serves as a general-purpose conversational agent only.
- No direct memory, multi-turn history across sessions, or user identity persistence—context is session-scoped.
- Tool approvals are subject to ACP permission policy (deny or allow_once per call).
- Model evaluation and routing are governed by available keys or Model Runner host configuration; fixed provider selection requires explicit YAML override.
- No installation/configuration steps are prescribed here; see Docker Agent documentation for deployment and configuration examples.

## Failures and Error Handling
- If required model keys are missing, the server fails to load/start and will return an error to the ACP client accordingly.
- Unsupported input types (non-text) or requests for non-configured business tools will be rejected.
- Any authentication or protocol negotiation failures will surface as errors to the ACP client.
