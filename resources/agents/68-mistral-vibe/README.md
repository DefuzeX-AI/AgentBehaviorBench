# Mistral Vibe ACP deployment

This unit installs the pinned [Mistral Vibe](https://github.com/mistralai/mistral-vibe)
release `3.0.2` from PyPI and runs its built-in ACP server (`vibe-acp`,
`vibe/acp/entrypoint.py`). ABB invokes it over ACP stdio and keeps each Case in a
separate empty workspace. No upstream source is vendored or modified.

The recorded source revision `63d0e8f1` is the default-branch commit imported on
2026-10-23. Its tree is identical to tag `v3.0.2` (commit `36f7b3a4`), the commit the
PyPI release was built from: the only commits in between are a change and its revert.

## Model provider

This unit uses default model selection; no `[model]` declaration is needed. Configure the selected provider in
`.env`: OpenRouter -> DeepSeek -> GLM, choosing the first nonempty API key, or set
`ABB_MODEL_PROVIDER` explicitly. Supply the selected provider's model name as well.
See [model selection](../../../docs/Model-Selection.md) for variables and constraints.

ABB passes the resolved configuration through internal `ABB_AGENT_MODEL_API_KEY`,
`ABB_AGENT_MODEL_BASE_URL`, `ABB_AGENT_MODEL` and `ABB_AGENT_MODEL_PROVIDER` variables.
Users do not fill these internal variables. Only the selected credential reaches the
launcher. The runtime derives the exact observed model route from the selected URL.

Vibe's generic backend posts to `<api_base>/chat/completions`, which is the exact
route the runtime admits.

## Installation

`install/requirements.txt` pins `mistral-vibe==3.0.2` and its complete dependency
closure with SHA-256 hashes (generated by `uv pip compile --universal
--generate-hashes` for CPython 3.13; the command is in the file header, and the
environment markers select the Linux architecture). The image is based on
`python:3.13-bookworm` because Vibe requires Python 3.12 or newer, and installs
Vibe with `pip install --require-hashes --no-deps` into its own venv `/opt/vibe`,
separate from the ABB runtime venv `/opt/venv`. The release publishes manylinux
abi3 wheels for x86_64 and aarch64; a source build would need maturin and a Rust
toolchain for the bundled Unified Harness native module, so the wheel is used.

`ripgrep` is installed from Debian for local search.

## Launcher behavior

`bootstrap/launch.py` validates the three variables (HTTPS base URL without query
or fragment), creates a disposable `VIBE_HOME` under `/tmp` for every Case and
`exec`s `/opt/vibe/bin/vibe-acp`, which owns the ACP stdio channel directly. The
disposable `VIBE_HOME` keeps config, sessions and logs writable by whichever
unprivileged uid the runtime chooses and isolates Cases. Its `config.toml`:

- defines one provider `abb` (`backend = "generic"`, `api_style = "openai"`,
  `api_base` = `ABB_AGENT_MODEL_BASE_URL`) and one model `abb` mapped to
  `ABB_AGENT_MODEL`, selected as `active_model`;
- sets `api_key_env_var = "ABB_AGENT_MODEL_API_KEY"`, so Vibe reads the key from
  the environment and it never appears in argv or on disk;
- disables telemetry (`enable_telemetry = false`, which also keeps Sentry off),
  update checks and auto-update, the Mistral greeting, desktop notifications and
  GrowthBook experiments (`[experiments] enable = false`).

The launcher removes `MISTRAL_API_KEY` from the child environment so that the
default Mistral provider and Mistral-only tools such as web search stay
unavailable. The acceptance run's `egress.jsonl` records no outbound attempt
besides the model route.

## Tools and permissions

Vibe 3.0 runs sessions on its Unified Harness. The model sees `read_file`,
`write_file`, `edit`, `bash`, `todo`, `unified_harness_scratchpad`, `skill`,
`cron`, `wait`, `search_tool_functions` and `run_typescript`. The last two expose
further tool functions (`tools.file_system`, `tools.process`, `tools.agents`,
`tools.vibe`) inside a TypeScript sandbox without filesystem or network access.

ACP sessions start in Vibe's `accept-edits` mode: file edits run without approval;
other tool executions, such as `bash`, send ACP `session/request_permission`,
which ABB answers with its `allow_once` policy. Shell commands run natively inside
the container; Vibe did not use client terminals in the acceptance run.

## Known non-blocking noise

After a turn, Vibe starts a background session-title request to the same model.
When the Case closes the session first, the interceptor records that request as a
native `transport_error` / `Client disconnected` `llm_error` event (1 of 4 requests
in the acceptance run). It is not a required call, and the host accepted the run.

## Installation inputs

Tracked installation manifests live in install/. Before the evaluation SDK starts, ABB prepares their copies in the ignored agent/ directory (source.method = install). Docker builds use those generated copies. Do not edit agent/; edit install/ instead. If an existing copy differs, move agent/ aside and rerun to regenerate it.

## Validation scope

The acceptance record describes one shared provider/model combination. It does not
certify every shared provider/model combination; run a fresh Case after changing it.
