# Kimi Code CLI ACP deployment

This unit installs the pinned [Kimi Code CLI](https://github.com/MoonshotAI/kimi-cli)
release `1.50.0` (tag `1.50.0`, commit `86f13642`) from PyPI and runs its built-in
ACP server (`kimi acp`). ABB invokes it over ACP stdio and keeps each Case in a
separate empty workspace. No upstream source is vendored or modified.

License: the upstream repository `LICENSE` at the pinned commit is Apache-2.0
(the ACP agent registry lists it as MIT; the repository file is authoritative).

The acceptance profile uses Zhipu GLM's OpenAI-compatible coding endpoint.
Supply these variables only at runtime:

- `GLM_API_BASE_URL`: the OpenAI-style base URL, e.g.
  `https://open.bigmodel.cn/api/coding/paas/v4`.
- `GLM_MODEL`: the exact provider model ID, such as `glm-5.1`.
- `GLM_API_KEY`: the Bearer credential. It is never written into this unit or to
  disk inside the container.

The interception manifest admits only the tested route:
`POST https://open.bigmodel.cn/api/coding/paas/v4/chat/completions`.
A different OpenAI-compatible provider needs an explicit reviewed route update;
changing environment variables alone does not broaden container egress.

## Installation

`agent/requirements.txt` pins `kimi-cli==1.50.0` and its complete dependency
closure with SHA-256 hashes (generated by `uv pip compile --generate-hashes` for
CPython 3.13 on x86_64 Linux; the command is in the file header). The image is
based on `python:3.13-bookworm` because Kimi requires Python 3.12 or newer, and
installs Kimi with `pip install --require-hashes --no-deps` into its own venv
`/opt/kimi`, separate from the ABB runtime venv `/opt/venv`.

`ripgrep` is installed from Debian. Kimi's Grep tool uses a system `rg` when one
is on `PATH`; otherwise it downloads a binary from `cdn.kimi.com` on first use,
which the interceptor would reject as undeclared egress.

## Launcher behavior

`bootstrap/launch.py` validates the three variables, creates a disposable `HOME`
under `/tmp` for every Case and starts `/opt/kimi/bin/kimi acp` with no options as
a child process (it relays the client's stdin; see "Client terminals" below).
The disposable `HOME` keeps `~/.kimi` (config, sessions, logs) writable by whichever
unprivileged uid the runtime chooses and isolates Cases. It writes:

- `~/.kimi/config.toml`: an `openai_legacy` provider pointing at
  `GLM_API_BASE_URL` and a default model `glm` mapped to `GLM_MODEL`, so ACP
  `session/new` uses GLM without a model choice. `default_thinking = false`,
  `telemetry = false`. `api_key` is left empty: the credential is passed as
  `OPENAI_API_KEY` (plus `OPENAI_BASE_URL`), which Kimi's `openai_legacy`
  provider prefers over the file, so it never appears in argv or on disk.
- a `PreToolUse` hook matching `^FetchURL$` that exits with code 2. Kimi's
  default ACP agent always loads the `FetchURL` tool, which issues direct HTTP
  requests outside the model route, and `kimi acp` accepts no `--agent-file` to
  drop it. The hook blocks the call locally and returns a tool error explaining
  that URL fetching is unavailable. (`SearchWeb` is skipped by Kimi itself
  because no Moonshot search service is configured.)
- `~/.kimi/credentials/kimi-code.json`: a placeholder OAuth token (see below).

It also sets `KIMI_DISABLE_TELEMETRY=1` and `KIMI_CLI_NO_AUTO_UPDATE=1`. Upstream
telemetry is on by default and posts to `telemetry-logs.kimi.com`.

### Upstream limitation: ACP requires a Kimi OAuth token file

In 1.50.0, ACP `session/new` calls `_check_token_usable()`
(`kimi_cli/acp/server.py`), which returns `Authentication required` unless a Kimi
Code OAuth token file exists, regardless of the configured provider. There is no
switch to skip this for third-party providers. The launcher writes a placeholder:

```json
{"access_token": "not-used-acp-gate-bypass", "refresh_token": "", "expires_at": 0,
 "scope": "", "token_type": "Bearer"}
```

It is only read by that presence check. No managed Kimi provider or Moonshot
service is configured, so nothing uses it for authentication, and the empty
`refresh_token` stops the background OAuth refresher from contacting Kimi's auth
server. `network.jsonl` of the acceptance runs shows only the GLM route.

### Client terminals are not advertised to Kimi

When the ACP client advertises `clientCapabilities.terminal`, Kimi 1.50.0 replaces
its Shell tool with one that calls `terminal/create` with the whole shell line in
`command` and no `args` (`kimi_cli/acp/tools.py`), e.g.
`command = "mkdir -p demo && echo ok"`. ACP defines `command` as the executable;
ABB's client executes it literally, so every Shell call failed with
`Error running tool: Internal error` in the first smoke run. There is no Kimi
switch for this. The launcher therefore relays the client's newline-delimited
JSON-RPC stream to Kimi's stdin and, in the `initialize` request only, sets
`clientCapabilities.terminal` to `false`; all other messages are forwarded byte for
byte, and Kimi writes ACP responses and logs directly to the launcher's
stdout/stderr. Kimi then keeps its native Shell tool, which runs the command via
bash inside the same container and workspace. Shell calls are still reported as
ACP `tool_call` updates, but no ABB `terminal_started` events are produced.
The client filesystem capabilities are unchanged.

## Known non-blocking noise

Kimi stops reading a streamed chat completion once it has the final message or a
complete tool call, before the provider's closing chunk. The interceptor records
those requests as native `transport_error` / `Client disconnected` `llm_error`
events (2 of 7 requests in the 3-step smoke run). They are not retried or
required calls, the responses are used by the agent, and the host accepted the
runs. Session titles are derived locally from the first prompt; Kimi makes no
background model call after a turn.
