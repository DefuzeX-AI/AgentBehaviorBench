# Case 复用、失败重试与多 Case 网页方案

状态：已获批准并实施；验证记录与实际边界见 [实施说明](Suite-Recovery-Implementation.md)。
代码基线：BBA `cda7b827c729f1f044fd1359ab316518c612c553`，PyPI `kuma-defuzex==0.2.4`。

目标：一次选择多个 Agent、每个 Agent 多个 Case。普通失败不阻断其他任务；已生成 Case 和已完成结果可复用；允许补跑未完成部分；网页在同一个 Suite 下同步显示进度、临时失败、重试和最终结果。

## 1. 沿用什么，需要补什么

沿用现有的共享 Case 线程池、协调线程、不可变 `PreparedCase`、独立执行目录、原子结果文件、每秒网页轮询以及单 Run 的输入/输出/Judge/OTel 详情组件。

目前的真实缺口：

- `prepare_cases()` 要求整批成功；需要返回部分成功和按 Case 位置记录的准备失败。
- 调度状态只存在于当前进程；需要持久化计划并从记录重建剩余任务。
- `CaseResult.status == failed` 同时包含 Judge 判出行为问题和运行故障；需要独立表示。
- 每个 Case 目前只有一份终态，缺少尝试历史；恢复不能覆盖原记录。
- 网页侧边栏已有 Case 列表，但评测正文只接收一个 Run。需要 Suite 的多 Case 总览及准确的尝试选择。
- Viewer 目前是只读 GET 服务。网页重试必须经受控命令入口交给调度器，不能只增加一个前端按钮。

这次范围包括 harness、SDK 通用契约、KUMA 插件、CLI/结果存储、observe API 和 web。通用调度及页面行为不放入 KUMA 插件。

## 2. 用户看到的运行单位

```text
Suite：本轮固定的测试计划
  Agent A
    Case 1：固定位置，生成后绑定原始 Case 文件
      Attempt 1：第一次执行的 Run、输入、输出、OTel、Judge
      Attempt 2：复用同一 Case 后的新 Run
    Case 2
  Agent B
    Case 1
```

- 逻辑 Case 使用 `(suite_id, agent_id, case_index)` 定位，即使生成尚未成功也有位置。
- Case 生成成功后，`case_id`、完整文件、内容摘要和文件摘要固定。
- 新执行产生新 `attempt_id`、工作任务 ID、SDK Run ID 和产物目录。
- 恢复同一个 Judge 请求属于原 Attempt 的恢复操作，保留原 SDK Run ID，另记恢复次数。
- 网页和汇总只按逻辑 Case 计数，重试不增加请求的 Case 总数。
- Case 文件只包含官方保存的 Case；执行输出、历史和证据属于对应 Attempt。

## 3. 如何复用 Case

生成方式保持官方公开流程：`create_run(...) → run.save_case(...) → run.cancel()`。
执行时使用 `create_run(case_path=...)`，不再请求 CaseGen。完整 Case 文件原样保存，不能只拿 prompt 或 case_id 重建。

准备阶段改为逐个保存、逐个确认接收：

1. Suite 启动时登记所有 Agent 和 Case 位置。
2. 一个 Case 保存成功后，核对官方格式、身份、重复内容和文件完整性。
3. 将文件放入 Suite 持有的稳定目录，持久化该位置的 `case_prepared` 记录。
4. 单个生成失败记录到对应位置；返回已准备 Case 和失败位置，其他 Agent 继续。
5. 调度器派发已准备 Case；后续补生成只接收缺少的 case_index，不能按成功列表重新编号。

例如需要 5 个 Case，已保存 1、2，生成 3 失败：1、2 可以执行；3 保留失败原因；尚未生成的位置仍可继续生成。恢复时只处理 3 和其他缺口，不重新生成 1、2。若遇到同一凭据额度或服务级阻断，则暂停受影响的生成任务，避免每个位置都重复失败。

保留当前准备任务共享线程池的方式。第一版不要求网页通过监听文件自行把正在生成的 Case 投入线程池；调度决策仍由协调线程统一执行。

`PreparedCase` 保留现有职责；准备返回值扩展为包含 `prepared_cases`、`failures_by_index` 和未尝试位置的批次结果。完整集合导入继续严格校验；新增逐 Case 校验用于接收部分集合，不能简单删除原来的数量检查。

## 4. 从哪里恢复

| 中断位置 | 默认处理 | 复用内容 |
| --- | --- | --- |
| Case 已生成，尚未执行 | 直接排队执行 | 原 Case 文件和顺序 |
| CaseGen 返回前断线，是否接受未知 | 先查询原请求；不能立即新建请求 | 原请求身份与账本 |
| 从未生成成功的 Case | 按原位置补生成；请求接受状态不明时先阻断 | 其他位置的 Case |
| 原已保存 Case 文件缺失或损坏 | 仅阻断该位置，恢复原始字节后继续；不偷偷换题 | 其他位置的 Case |
| Agent/容器执行出现明确可重试的暂时故障 | 清理上次资源后，新建 Attempt 执行同一 Case | 原 Case，独立新 Run/会话 |
| Agent 已完成，Judge 已接受但等待超时 | 恢复原 Judge 请求 | 原 Run、Submission、Evidence、请求账本 |
| Judge 已成功，宿主汇总前进程退出 | 校验已有报告和证据后补登记 | 原报告和原 Attempt |
| Judge 终态 `model_invalid_result` 等 | 标记需处理；不把失败请求当作仍在等待 | 保存全部已产生证据 |
| 报告已收到，但宿主拒绝 trace | 保留报告及拒绝原因；修复后再决定是否重跑 | 原报告作为历史，不伪造验收通过 |
| 多轮 Case 第 4 轮执行中断 | 第一版从该 Case 第 1 轮重跑 | 原题目、输入顺序；不拼接旧运行状态 |

KUMA 0.2.4 的 `resume_request()` 恢复请求，不重建任意 Run 和 Agent 内存。CaseGen 请求恢复也不等于能导出可加载 Case。没有可用文件时，须显示“需要补生成”，不能把请求状态成功直接当成 Case 已准备。

同样，没有经确认的公开“终态失败后仅重新 Judge”接口时，不承诺提供这种按钮。页面可以说明“原请求已失败；可在修复后重新执行此 Case”，但不能偷偷重放 Submission 或调用私有接口。

多轮重跑会使用新会话，从第一轮开始；旧输出和记忆只用于查看，不注入新会话。不同 Attempt 的 OTel、Submission、历史及 Judge 严格分开。

## 5. 重试规则

建议默认允许最多 2 次自动重试，即首次执行加最多 2 次，设置为 0 可关闭。这个上限仅作用于明确允许自动重试的故障，不表示所有 failed 都会重试。

- 错误判断使用阶段、类型、SDK code、请求状态及插件能力；不能只检查 `retryable` 或中文 message。
- SDK 内部 HTTP 重试沿用官方边界；BBA 不在外层绕过官方禁止自动重试的错误分类。
- 请求是否被接受不明时先核对原 operation。不能因超时立即重新付费提交。
- Agent 重跑需要确认上次容器及网络已清理，并且该 Agent 支持隔离重放；执行结果不明的外部写操作留待处理。
- Judge 的 `pass`、`issue`、`insufficient_evidence` 都是判决。`issue` 不自动重跑到 pass；证据不足单独展示，不能混入网络故障重试队列。
- 认证失败、额度耗尽、Case 完整性错误、确定的配置错误和 SDK 终态失败直接保留原因；需要处理后由用户重新触发符合能力的恢复。
- 重试等待采用退避，例如 5 秒、15 秒，加少量抖动；官方有适用的等待提示时优先遵守。
- 等待中的任务释放工作槽位；同一个共享并发上限限制准备、执行和恢复。一个逻辑 Case 同时最多一个有效任务。
- 明确区分 SDK HTTP 尝试、请求恢复和新 Case 执行 Attempt，记录实际请求与费用，避免多层重试次数相乘而不可见。

## 6. 状态如何展示

执行状态与 Judge 判决分别保存和展示。

```text
待生成 → 生成中 → 已准备 → 排队 → 执行中 → 等待 Judge → 已完成
                                ↓
                         临时失败 / 等待重试
                                ↓
                           正在重试 → …
                                ↓
                      重试耗尽 / 需要处理

任何阶段可记录：已取消、进程中断、状态核对中。
```

“临时失败”表示上一次尝试确实失败，并且已经安排下一次恢复；不是把所有错误临时改名。网页显示阶段、原因、下一次时间和重试次数。

样例：

| Case | 执行状态 | Judge | 尝试 |
| --- | --- | --- | --- |
| ReAct / Case 1 | 已完成 | pass | 1 |
| ReAct / Case 2 | 已完成 | issue | 1 |
| ReAct / Case 3 | 临时失败，5 秒后重试 | 尚未获得 | 1，已安排第 2 次 |
| Trading / Case 1 | 正在重试，第 2 轮 / 共 5 轮 | 等待执行完成 | 2 |
| Research / Case 1 | 需要处理：Judge 终态失败 | 尚未获得 | 1 |

另保留 `host_acceptance`、证据状态和报告是否收到。Judge 报告存在但宿主拒绝时，页面不能显示为已验收完成。

## 7. 网页布局与同步

默认进入 Suite 总览：

```text
Suite ABC · 3 个 Agent · 15 个 Case · 并发上限 3
已完成 8 | 运行 3 | 等待重试 1 | 需处理 1 | 排队 2
已收到 Judge 报告 8 / 15（判决分布另列）

[全部 Agent ▼] [全部状态 ▼] [仅看需处理] [继续未完成] [导出当前报告]

Agent      Case     当前阶段        执行状态       Judge    尝试    操作
ReAct      1        完成            已完成         pass     1       查看
ReAct      2        完成            已完成         issue    1       查看
ReAct      3        Agent 执行       5 秒后重试      —        1       详情
Trading    1        第 2/5 轮        正在重试        —        2       详情
Research   1        Judge           需要处理        —        1       原因
…所有 15 个位置从开始就存在，不要求先产生 Run 目录
```

展开一个 Case 后，复用现有详情组件，显示该 Attempt 的 Case、每轮输入/输出、SDK Submission、Judge 和 OTel；增加“第 1 次 / 第 2 次”切换。支持展开多个 Case 查看，不要求把所有原始 trace 同时加载。

详情绑定 `(suite_id, agent_id, case_index, attempt_id)` 和准确的 `artifact_run_id`。当前侧边栏使用 Agent + case_index 找第一份 Run 的方式要替换，避免重试后打开旧记录或混入别的 Suite。

同步仍用 `useLiveJson` 的约 1 秒轮询。总览读取统一 Suite 快照，带递增 revision；Case 详情按需加载。前端不根据过期 Run 状态自行覆盖 Suite 当前状态。断线保留已显示内容并提示连接状态；重新连接拉取最新快照，不能把网页断线当作 benchmark 失败。已经打开的历史 Attempt 不自动跳到新 Attempt。

生产 Python Viewer 与 Vite 开发页面消费同一份状态协议；Vite 通过本地后端代理获得 Suite/控制能力，避免 Node、Python 各写一份调度规则。独立查看原始 Run 的只读模式继续存在。

## 8. 持久化与崩溃恢复

建议新增 Suite 存储服务，将目前 CLI 内的通用事件写入能力下沉到 harness 可调用层，继续使用本地文件。

```text
results/suites/<suite_id>/
  plan.json             # 固定 Agent 选择、位置、非秘密配置与版本指纹
  events.json           # 按序记录状态转移，原子发布 JSON 数组
  cases/<agent>/<slot>/  # 不可变的官方 Case 文件
```

原来的 `results/observe/<artifact_run_id>/` 继续保存 Attempt 产物与 `sdk-repo/.kuma` 请求账本；Suite 记录精确引用。清理操作要识别这些引用，不能删除尚可恢复 Suite 所依赖的产物。

- 计划先落盘，再派发。Case 文件成功发布后，再记录已准备；Attempt 派发记录必须在启动执行前持久化。
- 状态转换只由持有 Suite 锁的协调器写入；文件锁覆盖多个进程，防止同时开两个 resume。
- 新事件带 schema version、递增序号和 Attempt 身份。快照/汇总由事件归并产生，不能单独修改并形成第二套真相。
- 崩溃后先核对记录、原容器状态、已保存产物和 SDK 请求。不能将磁盘上的 running 直接当作新任务重新派发。
- 容器未退出或请求状态不明时显示“状态核对中”；资源清理完成或安全恢复方案确定后才能推进。
- 恢复沿用原 Suite ID。追加恢复事件与新 Attempt，不覆盖旧错误；旧 suite_completed 事件不能把恢复后的任务重新标为终态。
- 继续原 Suite 时验证 Agent 源码、输入映射、镜像/依赖、模型与运行配置指纹。纯续跑保持原配置；修复代码或更换模型后使用关联的新 Suite，可复用同一份 Case，避免把不同配置的评分混成一组。
- `.env` 和 API Key 不写入计划或网页。请求恢复按 SDK 要求使用原 Backend 和原凭据；凭据变化导致不能恢复时明确解释。
- 对只有旧事件、没有完整计划的历史记录允许查看；仅在恢复依据齐全时提供恢复，不能猜测缺失配置。

## 9. 终端与网页使用同一个恢复入口

拟新增命令，名称供审阅：

```text
agentbench resume <suite-id>
agentbench retry <suite-id> --agent <agent-id> --case 3
```

`resume` 处理未开始、中断和具备恢复条件的未完成位置；已经完成但 Judge 为 issue 的 Case 不进入该列表。`retry` 明确选择一个失败位置，实际采取“补生成 / 重跑 Case / 恢复原请求”中的合法动作。终态 Judge 重评没有官方能力时，返回原因和可选的“重新执行此 Case”，不能悄悄替换行为。

网页按钮调用同一 Suite 控制服务，提交选择及幂等 command_id 后返回已接收状态；协调器验收命令并更新事件。重复点击、两个窗口同时点击都不能重复创建任务。

运行中的协调器接收命令；没有协调器时，受控恢复入口先获取 Suite 锁，再启动恢复会话。Viewer HTTP 请求线程不能直接启动容器。关闭网页不取消任务；CLI Ctrl-C 停止当前恢复并保存进度。

新增控制接口只接受同源、绑定当前 Suite 的命令及会话控制凭据，不接受任意命令行、文件路径或浏览器传入的 API Key。仅查看导入文件或只读历史记录时不显示可执行按钮。

## 10. 报告与测试口径

报告每个逻辑 Case 一行，展开保留全部 Attempt；正式结果取按照规则完成并验收的执行，不挑最高分。恢复原请求后的报告归回原 Attempt。已完成 Case 不自动重评。

报告同时给出：计划 Case 数、执行完成数、收到报告数、宿主验收数、失败/中断/待恢复数，以及 pass/issue/insufficient_evidence 分布。重试成功仍可追踪曾失败过几次。运行中或部分失败时能导出部分报告，清楚标明尚缺的结果。

必要测试：

1. 生成 5 个中的第 3 个失败：其他成功文件保留且可执行，补生成不重复 1、2。
2. 一个 Case 暂时失败后成功：其他 Case 继续；只有失败位置新增 Attempt，Case ID/摘要不变。
3. 30 个 Case 中已完成 20 个后重启：只处理剩余位置，含派发前后及结果保存前后的崩溃点。
4. Judge 请求已经接受后断线：恢复只查询原请求，Agent 调用次数和 Judge POST 次数不增加。
5. Judge issue 不重试；model_invalid_result 不进入无限循环；宿主拒绝的报告保留但不计为已验收。
6. 第 4 轮中断后重跑：新 Attempt 从第 1 轮开始，上下文、OTel 和报告不跨 Attempt 混合。
7. 两个页面/进程同时恢复、重复命令、乱序历史读取：只执行一次且页面选择准确。
8. 自动重试耗尽、用户取消、磁盘写入失败、容器清理失败：保存明确状态且不重复派发。
9. UI 展示多个 Agent 的全部 Case；真实状态变化覆盖等待重试、重试中、恢复成功和需要处理；刷新与断线恢复后保持一致。
10. 固定 Case 集下进行 3 Agent × 3–5 Case 的真实容器验收，保留输入、输出、Judge、并发和恢复记录，并计入既有测试预算。

已经有上游 Issue 编号的回归继续放进 `test_issue<N>*.py`，补充恢复场景；这项新需求如果尚无 Issue 编号，先使用 `test_suite_resume.py`、`test_case_retry.py` 等明确名称，关联真实 Issue 后再按编号命名，不能编造 Issue。

## 11. 分阶段交付

1. **Case 复用与持久化**：固定计划、按位置保存、部分生成成功、执行状态与判决分离；先证明重启不会重跑已完成 Case。
2. **恢复调度与 CLI**：尝试历史、失败分类、有限重试、请求恢复、原 Suite 汇总更新。
3. **网页闭环**：Suite 多 Case 总览、Attempt 详情、实时状态、恢复按钮和部分报告。
4. **完整验收**：故障注入、SDK 边界回归、Web 交互验证、真实多 Agent 多 Case 验收。

每个通过验收的实施阶段单独提交并 push 到 fork，说明已完成能力和仍缺的能力。验收结果以实施说明为准。按 2026-09-14 用户补充要求，记忆与多轮对话设计问题暂缓，后续验收先采用单轮。
