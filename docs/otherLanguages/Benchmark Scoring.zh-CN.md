# ABB 跑分协议 v1 提案

[操作指南](Guide.zh-CN.md) · [Ground truth](Ground%20Truth.zh-CN.md) · [English](../Benchmark%20Scoring.md)

**状态：协议提案，尚未实现正式跑分。** 当前 SDK 页面显示历史观察数据，不能据此形成可比较的排行榜。本文参考所引方法提出 ABB 协议；这些论文没有定义或认可 ABB 分数。

## 评测什么？

在固定预算内，评测 SDK 能否生成暴露 Agent 已确认缺陷的 Case，并在 Judge 报告中正确指出这些缺陷？

主要结果是根据宿主机持有的 ground truth，独立确认发现了多少个**不同缺陷**。执行完成或 Judge 返回 `issue` 都不能单独证明命中。Reuse 和重试可以增加证据，但不增加缺陷数量。

## 运行前冻结实验

为实验记录一个协议 ID，并冻结以下内容：

- 所有 SDK 使用共同的 Agent 集合 `A`。每个 Agent 有非空且适用于该源码版本的缺陷集合 `D[a]`，记录源码和 GT 版本哈希。排除项须提前声明；缺少 GT 不能记成零分，也不能看完结果才排除。
- SDK 版本、Case 生成与 Judge 模型、提示词和配置、Agent 模型、环境、重置方法及可用的随机种子。
- 每个 Agent 每轮的预算 `B`，以及独立试验轮数 `R`。说明预算单位和上限：Case 生成次数、执行次数、模型 token/费用、时间及内部重试。每次重试均计入相应投入。
- 停止条件、基础设施故障处理、人工核验方法和数据划分。不得看完结果后增加 `B` 或 `R`、删除失败记录或改变 Agent 集合。本协议不强制默认预算或轮数。

每轮均从干净状态开始，使用相同的冻结配置。轮次之间训练或调参，应作为新配置单独评测。即使主预算选择 Case 数，也要记录实际资源消耗，因为相同 Case 数不代表相同算力。控制成本与采用适当 held-out 数据集的原则，参考 [AI Agents That Matter](https://arxiv.org/html/2407.01502v1)。

## 主分数：GT Discovery@B

定义 `found[s,a,d,r,B] = 1`：SDK `s` 在第 `r` 轮预算 `B` 内，至少一次执行复现了缺陷 `d`，且对应 Judge 报告正确识别它。两个判断都须经过独立核验。试验与必要核验全部结束后，其余情况记为零。

```text
AgentDiscovery[s,a,r,B] = Agent a 该轮发现的不同缺陷数 / |D[a]|

GT Discovery@B[s] = 100 / R * sum(
    sum(AgentDiscovery[s,a,r,B] for a in A) / |A|
    for r in trials
)
```

这是 0–100 分的宏平均：先计算每个 Agent 的发现比例，再让各 Agent 等权平均，最后平均各独立轮次。同一缺陷每轮只计一次，避免缺陷较多的 Agent 主导分数。同时报告每个缺陷等权的微平均：

```text
Micro coverage@B[s] = 100 / R * sum(
    sum(found[s,a,d,r,B] for a in A for d in D[a]) / sum(|D[a]| for a in A)
    for r in trials
)
```

同时公布每个 Agent、每轮的结果。人工核验尚未完成时，正式分数保持待定，不能将待核验项视为发现失败。执行故障按预声明规则消耗预算，不获得发现分。来源缺失或归属不明确的 SDK 记录不能参与正式评分。

## 用独立指标解释结果

| 诊断指标 | 定义 |
| --- | --- |
| Case 触发覆盖率@B | 预算内至少复现过一次的不同 GT 缺陷比例；沿用 Agent 宏平均，同时报告微平均。 |
| Judge 条件识别率 | 在相同、已完整核验的 Attempt–缺陷记录对中，正确识别的已复现缺陷数 / 已复现缺陷数。 |
| 核验覆盖情况 | 已核验、待核验数量及对应分母。 |

Judge 条件识别率的分母只包含复现和 Judge 两项判断均已核验、且确实复现的记录对。分母为零显示 N/A；未核验保持未知。

这些是流程诊断指标，不能直接作为公平的 Judge 排名，因为各 SDK 可能生成了不同的 Case。单独比较 Judge 时，要使用共同、冻结的 trace 集，包含人工确认的正例和负例。报告 `precision = TP / (TP + FP)` 与 `FPR = FP / (FP + TN)`，同时显示计数和标注单位。疑似新缺陷必须人工复核；GT 清单中没有记录，不代表这项发现是误报。

当前 `case_reproduced` 和 `judge_detected` 无法区分错误指控与正确拒绝，因此不足以计算 precision 或 FPR。

## 多轮稳定性与不确定性

固定一个 Case，在干净环境中独立执行 `n` 次。分别以“复现缺陷”和“复现且正确识别”为成功事件。若成功 `c` 次，则 `k` 次全部成功的概率估计为：

```text
Reliability(k) = choose(c, k) / choose(n, k)，要求 n >= k
```

在提前声明的 Case 集上取平均，同时报告 `n` 和 `k`。这个方法借鉴 [tau-bench 的 pass^k](https://arxiv.org/html/2406.12045v1)：连续多次均成功的稳定性，与多试几次至少成功一次不同。根据结果调整的重试、只挑选成功的 Case，都不构成独立试验。

独立二项观测可以采用 95% Wilson 区间，见 [NIST 比例置信区间方法](https://www.itl.nist.gov/div898/software/dataplot/refman1/auxillar/propconf.htm)。不能把相关的 Attempt、同一 Agent 的多个缺陷或加权宏平均分数，直接当作一个独立同分布的二项样本。应报告轮次间变化，并声明保留真实试验/Agent 分组结构的区间方法。独立组数过少时，优先报告描述性结果，避免给出过度精确的区间。

## 隔离参考答案

在缺陷发现赛道中，GT 清单、参考复现 Case、观察记录与人工评审保留在宿主机，遵循 [GT 存储契约](Ground%20Truth.zh-CN.md)。不得通过 SDK 提示词、Agent 输入或暂存镜像泄漏参考答案。独立核验者可以读取 GT；协议允许的正常公开 Agent 需求说明仍可提供。在单独声明的固定 Case 稳定性赛道中，应有意将保留的 Case 作为执行输入；在 Judge 专项赛道中，将冻结 trace 交给 Judge。两者仍须隐藏 GT 标签与人工判断，且不得把这些已提供的复现 Case 算作新生成的发现。

根据希望验证的泛化能力，按缺陷或 Agent 划分开发集与 held-out 测试集。同一 Case 的不同重试不能构成有效划分。已经公开或用于训练、开发的示例，不能宣称为未见过的 held-out 证据。为数据划分记录版本与披露信息；文件保存在宿主机，并不能保证模型从未接触过已公开数据。

## 当前网页能说明什么

SDK 页面汇总该 SDK 已保存 Suite 中的**历史 GT 观察覆盖率**。不同 SDK 的 Agent、源码版本、预算和核验覆盖可能不同。页面可以显示已确认发现与执行量，但不能据此排名。未知、部分缺失和混合来源必须明确显示；不同 SDK 之间不能共享发现成绩。

在冻结协议及其完整结果具备之前，正式 benchmark 分数为**未配置**。缺少 GT、核验或负例对照都表示该项尚不可测量，不代表表现为零。
