# 用户的想法：先验证评测器，再评测 Agent

## 核心问题

ABB 首先需要验证 DefuzeX SDK 是否是一把可靠的“尺子”。建议将核心研究问题定义为：

> 给定明确的 Agent 能力描述和一次真实执行，DefuzeX SDK 能否稳定、完整、可复现地发现 Agent 的行为缺陷，并正确说明判决依据？

SDK 目前同时参与 Case 生成、执行协议、证据采集和 Judge 判决，因此不能直接用最终 verdict 证明 SDK 自身准确。应先分别验证以下四项能力。

## 1. CaseGen 质量

CaseGen 是被测组件之一，建议衡量：

- 职责符合率：Case 是否测试 Agent 声明的能力；
- 可执行率：Case 是否提供必要输入和可用工具；
- 可判定率：成功和失败是否有明确、可观察的区别；
- 行为覆盖率：Requirement 中的行为有多少被覆盖；
- 虚构依赖率：是否要求不存在的工具、文件或服务；
- 多样性：多个 Case 是否只是同一模板的改写。

这些指标应由独立人工标注或冻结的 Gold Labels 评估，不能由 CaseGen 或同一 Judge 自行确认。

## 2. Judge 质量

使用人工确认的 Gold Cases 和已知结果测试 Judge，样本应覆盖：合规、明确违规、证据不足、Agent 失败、基础设施失败、伪造引用、部分完成和任务无关等情况。

建议衡量：

- 缺陷检出率与误报率；
- status 和 severity 分类准确率；
- Step 归因准确率；
- evidence gap 识别率；
- 重复判决及不同 Judge 之间的一致性。

Judge 的目标是面对独立真值给出正确判决，而不是与自己生成的 Case 保持自洽。

## 3. SDK 证据管道

证据链可以进行确定性测试：

```text
Agent 实际产生
    ↓
SDK 捕获
    ↓
白名单过滤
    ↓
Submission 封装
    ↓
Judge 接收
```

通过植入已知 output、span 和字段，测量 span 捕获率、字段保留率、丢弃率、截断率、Step 与 evidence 的关联正确率，以及错误阶段归因是否正确。

## 4. 端到端缺陷检测

在完整流水线中使用已知缺陷实验组，例如：

- Control：完全符合要求；
- Defect A：未调用必需工具；
- Defect B：编造工具结果；
- Defect C：遗漏步骤；
- Defect D：输出正确但 trace 缺失；
- Defect E：Agent 正确但 SDK 丢失证据。

由此计算真阳性率、假阳性率、缺陷类型识别率、根因归属准确率，以及 CaseGen、Agent、Evidence、Judge 各阶段对失败的贡献。

## 建议实施顺序

1. 建立独立的 Gold Cases、Gold Executions 和人工真值；
2. 分别验证 CaseGen、Judge 和证据管道；
3. 用植入缺陷完成端到端验证；
4. 达到预设门槛后冻结 SDK、Case、Judge 和配置版本；
5. 使用通过资格验证的评测器正式评测 Agent。
