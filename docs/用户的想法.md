## 1. 当前阶段：先让 Agent 独立运行

- 暂时不执行评测 SDK，不先做 Case 生成、submit 或 Judge。
- 先打通 Agent 的准备、启动、输入、执行、输出和结束流程，再做下一步。
- 当前先检查 Wangyi 的实际实现并讨论需要修改的边界，不因本次讨论直接启动完整评测。
- 后续 SDK 接入应复用 Agent 的执行实现，避免出现冒烟和正式评测两套不同调用线路。

## 2. 不强制使用 CLI

- 不要求所有 Agent 都具有 CLI，不把 CLI 或 旧标准输入输出通信协议 作为唯一 Agent 接入方式。
- Agent 应能保留原生调用方式，例如 Python 函数、异步接口、框架图、服务或自身已有命令。
- ABB 自身可以提供 CLI 和 Python library 两个入口，共用执行核心。
- “保留 CLI”不等于“强制所有 Agent 通过 CLI 调用”；具体统一接口尚待讨论。
- 用户此前指出 LangGraph adapter 似乎未进入实际执行线路，需要在重构时明确框架适配与运行环境的关系。

## 3. 原生 Agent 来源与接入

- 希望像 Wangyi 的组织方式一样，以下载链接及版本信息描述 Agent 来源，获取原生 Agent。
- 不应要求用户把 Agent 改造成 ABB 专属实现才能使用。
- 接入说明、必要适配及环境准备应清楚记录；不能把下载完成等同于 Agent 已运行成功。
- 下载声明、运行配置和 adapter 的最终结构尚未确定。

## 4. SDK 保持可替换，放到后续阶段

- 不将 Kuma / Defuze SDK 硬编码为 ABB CLI 或核心的唯一选择。
- 用户应能在自己的接入代码中选择 SDK，期望有类似 sdk=xxx 的接口，并有接入教程。
- CLI 和 Python API 应复用同一套 SDK 接入能力。
- SDK 的导入可替换与接口兼容是两件事；不同 SDK 可能需要适配，不能宣称只改 import 即可兼容所有 SDK。
- Defuze 正式模式要求 SDK 与 Agent 同容器；后续设计必须安排正确的执行位置，不能用 allow_local=True 代替解决部署问题。

## 5. Trace 与网页视图

- 用户明确需要 OTel 跨进程采集。
- 希望看到更具体的执行视图，包括 Agent 过程、trace、输入输出及结果。
- 用户提出使用 React 等前端展示网页，并讨论 Python 与前端之间的数据契约和通信方式。
- React、FastAPI、HTTP/SSE、Collector、存储选型尚未被确认为最终实现方案。
- 原始 trace、网页展示数据、交给 SDK Judge 的证据需要明确关系；当前阶段不执行 SDK。
- 2026-09-08 补充：用户明确希望网页像“手术台”，能查看 Agent 的功能，并观察一次真实执行中的工具使用、LLM 调用和完整 trace。页面主要定位为 Agent 执行观察台；被测网页的截图、DOM 回放尚未明确要求。

### 5.2 页面与采集的具体化建议（助手提出，待实现时确认）

- Agent 信息区：来源、版本、输入要求、已声明或已发现的能力及工具；标明信息来源，区分“具备的能力”和“本次实际调用”。
- 输入区：公司名称、运行按钮、当前状态。
- 过程区：按父子关系显示调用树，同时显示时间线，保留并行分支、重试、错误和取消。
- 详情区：点击节点查看输入、输出、工具参数与返回值、模型、耗时、可获取的 token 用量；大内容通过附件展开。
- 结果区：最终研究报告及 Agent 实际提供的来源引用。
- 历史记录：一次执行有稳定的 run_id，刷新页面后仍能查看过程和结果。
- “所有 trace”应落实为明确的采集覆盖范围：Agent 根调用、框架节点、子 Agent、模型请求、工具调用和错误；没有采集到的部分标为未知或缺失，不能显示成“没有发生”。
- OTel 是采集和传输体系，trace/span 是关联后的执行记录，LLM 监控是对模型调用记录的专门视图；避免把它们设计成互不关联的三套结果。
- 只靠模型 HTTP 请求不能还原所有工具、节点和子 Agent 行为，需要框架适配或 instrumentation；跨进程调用还需要传播上下文并接收远端 spans。
- 页面详情展示实际可采集、允许展示的请求与响应，密钥等认证数据须脱敏；不承诺获得模型未暴露的内部推理。
- 本阶段的原始执行观测应独立于未来 SDK Judge 的证据筛选与裁剪。

示意流程（用于解释界面，不是已运行记录，也不保证上游 Agent 固定采用这些步骤）：

```text
输入公司名称
→ Agent 根调用
  → 规划 / 模型调用
  → 公司、行业、财务或新闻研究分支
    → 搜索工具调用
    → 页面读取工具调用
    → 模型分析
  → 汇总 / 模型调用
→ 最终研究报告

各调用的运行事件和 spans
→ 关联到同一次执行并保存
→ 网页调用树、时间线和详情
```

## 6. Wangyi 代码核对（事实记录，非自动采纳的设计）

本次核对了 README、tools/CONTRACT.md，以及 tested/015 Company Research Agent 的 runtime/entrypoint.py、runtime/run.sh 和 run_case.py。

### 启动命令和 Agent 调用是两层

Wangyi 仍使用 run.sh 和 Docker 命令启动环境，因此不能说它完全不依赖命令行。但不要求每只 Agent 暴露统一 CLI：所检查的 015 adapter 通过 Python Graph 对象和异步 graph.run(...) 执行上游逻辑。

```text
run.sh smoke
→ 启动 Agent 容器
→ entrypoint.main()
→ build_tracer()，只挂原始 span exporter
→ run_agent(payload, tracer)
→ Python Graph.run(...)
→ 输出结果、原始 spans、运行元信息
```

正式 SDK 评测复用同一个 run_agent：

```text
宿主机 run_case.py
→ run.sh exec：把评测脚本放入 Agent 容器执行
→ 容器内导入 Kuma 和 entrypoint
→ build_tracer(configure=SDK 的采集配置函数)
→ SDK 获取 Input
→ entrypoint.run_agent(...)
→ SDK 提交及评判
```

### 可借鉴的边界

- 环境启动层：准备镜像、挂载、环境变量和容器生命周期。
- Agent 调用层：处理实际调用、结果提取和框架到 OTel 的桥接。
- SDK 评测层：处理 Case、Input、Submission、Judge。
- 单独运行 Agent 不需要创建 SDK Run；但这份 Wangyi 镜像构建脚本仍安装 Kuma，因此“运行不调用 SDK”不等于“安装依赖也已剥离”。
- 所检查的 015 adapter 还替换了模型客户端和 Tavily 搜索实现，不能把它的冒烟流程描述成完全未经适配的原生执行。

## 9. 先聚焦 LangGraph Agent（2026-09-08）

### 用户明确的研究范围

- 先从 LangGraph Agent 开始，减少同时研究多框架造成的混乱。
- 先查看 LangGraph 官方文档，再讨论接入；当前仍以原生 Agent 执行、网页观察及跨进程 trace 为目标。
- 这是第一阶段的范围收敛，不据此认定 ABB 永久只允许 LangGraph。

### 官方文档核对结果

- LangGraph 是编排运行库，可以独立使用；已编译的 graph 可直接 invoke/ainvoke 或 stream/astream。CLI 和 LangSmith 平台不是调用 Python graph 的前提。[Overview](https://docs.langchain.com/oss/python/langgraph/overview)
- Graph API 以 State、Node、Edge 组织执行。Node 是函数，可以包含模型、工具或普通代码；节点名不能自动代表全部业务能力。应区分图结构、本次真实执行、Agent 作者声明的能力。[Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)
- compiled graph 提供输入 JSON Schema 接口，可用于了解输入形状；不能假设所有研究 Agent 都接受 messages 或 company_name，也不能仅靠 schema 推断业务语义。[get_input_jsonschema](https://reference.langchain.com/python/langgraph/graph/state/CompiledStateGraph/get_input_jsonschema)
- Streaming 的 updates 提供步骤状态增量，messages 提供模型输出片段及元信息，custom 需要代码主动写事件；subgraphs=True 用于纳入子图事件。tasks/checkpoints 文档要求 checkpointer。它们不能自动覆盖节点中任意外部 SDK 或远程服务内部的执行。[Streaming](https://docs.langchain.com/oss/python/langgraph/streaming)
- 官方有 React useStream 和图执行 UI 模式。apiUrl/assistantId 示例面向配套服务 API；自己写任意 SSE 接口，不代表直接兼容该 hook。可以选配套 Agent Server，也可以由 ABB 自己提供服务与匹配的前端客户端。[LangGraph Frontend](https://docs.langchain.com/oss/python/langgraph/frontend/overview)、[Frontend Overview](https://docs.langchain.com/oss/python/langchain/frontend/overview)、[Agent Server](https://docs.langchain.com/langsmith/agent-server)
- 官方支持把 trace 导向其他 OTel 后端。跨进程需 inject/extract 上下文，并让相关进程产生、上传 spans；仅修改 exporter 地址不能填补未采集的调用。LangSmith 自有分布式 headers 与 OTel 传播方式需按实际采集链路区分。[OTel](https://docs.langchain.com/langsmith/trace-with-opentelemetry)、[Distributed tracing](https://docs.langchain.com/langsmith/distributed-tracing)
- Checkpointer 用于状态保存、恢复等；它与观测记录的持久化职责不同。[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

### 当前文档的版本边界

- Streaming 页面注明 version="v2" 格式要求 LangGraph >= 1.1；另有 stream_events(version="v3") 文档，基础 streaming 页面仍有 preview 提示。接入应先核对上游 Agent 的锁定版本，不混用新旧格式，也不默认升级上游依赖。[Streaming](https://docs.langchain.com/oss/python/langgraph/streaming)、[Event streaming](https://docs.langchain.com/oss/python/langgraph/event-streaming)
- 前端新文档使用 @langchain/react；旧页面仍有 @langchain/langgraph-sdk/react，需匹配版本。
- OTel 指南仍展示 LANGSMITH_OTEL_ENABLED；另一个官方页面已介绍 tracing_mode / LANGSMITH_TRACING_MODE 的 langsmith、otel、hybrid 选择，并标记 Client.otel_enabled 参数弃用。实施前需核对实际 SDK 版本和导出路径，不拼接不同代配置。[Tracing destinations](https://docs.langchain.com/langsmith/log-traces-to-project#route-between-langsmith-and-opentelemetry-destinations)

```text
加载一只真实 LangGraph Agent 的 graph / factory
→ 按它自己的输入 schema 传入公司研究任务
```

### 9.1 具体样本：Wangyi 第 015 个 Company Research Agent

用户指定 Wangyi 的第 15 个 Agent。已定位 `wangyi/agents/tested/015_guy-hartstein__company-research-agent`，其目录主要包含适配运行文件。另在 `Agent/company-research-agent` 找到对应项目的本地源码副本；README 指向 guy-hartstein/company-research-agent。ABB 的 `resources/agents/01-company-research-agent/backend/graph.py` 与该源码副本的 graph.py SHA256 相同；这不代表整个目录或 Wangyi 历史镜像的版本完全相同。

本轮源码核对：

- `backend/graph.py` 的 Graph 包装 StateGraph，构造时接收 company、url、hq_location、industry、job_id。Graph.run(thread) 内部 compile 后调用 compiled_graph.astream(input_state, thread)。
- 工作流为 grounding → 四个并行研究分支（公司、行业、财务、新闻）→ collector → curator → enricher → briefing → editor。
- 项目已有 React + FastAPI：application.py 的 POST /research 创建 job_id 和后台任务，调用 Graph.run；ui/src/App.tsx 通过 EventSource 连接 /research/{job_id}/stream。虽然 README 写 polling，当前前后端代码实际使用 SSE；轮询发生在服务端读取内存 job_status 的循环里。
- SSE 读取并移除 job_status 中的事件，提供业务进度；不能据此声称已经具备可持久查询的完整 trace 或多客户端事件回放。
- Wangyi 的 entrypoint.py 在 graph.run 的配置中传 callbacks=[SpanEmitter]。回调按 LangChain run_id/parent_run_id 创建、关联和结束 OTel spans，默认经内存 exporter 留档；这一段没有实现跨进程 OTLP 采集链路。
- Wangyi 入口会替换 OpenAI/Gemini 客户端，并把 Tavily 客户端替换为固定 OpenAI 文档的 stub；不能以此证明任意公司真实搜索已经工作。其启动脚本还启用了 sitecustomize provider shim，完整行为需考虑加载顺序。
- 采集覆盖待核验：研究节点直接调用 AsyncTavilyClient.search/extract/crawl；LangChain 的 on_tool 回调本身不保证捕获这些普通 SDK 方法。SpanEmitter 还对部分输入输出截断到 4000 字符，node spans 不保存节点输入输出。因此当前留档不等于无损的“所有 trace”。

后续以该真实 Agent 的业务执行为基准，借鉴 Wangyi 的 callback 接入位置，逐项验证模型、搜索和跨进程覆盖。本次只阅读代码和记录，没有运行或修改 Agent。

### 9.3 启动前缺口核对（2026-09-08）

用户下一步希望启动这只 Agent，询问当前 benchmark 缺少什么。本轮只做启动前检查，不安装、不调用外部模型或搜索。助手最初错误地按本机直连供应商分析；用户随后明确纠正必须使用现有 Docker + Interceptor + OpenRouter 链路，以下记录已修正。
